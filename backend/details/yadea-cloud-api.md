# 雅迪云 API 接入

## 当前结论

按雅迪云 API 接入设计. 目前没有取得可验证的企业 API 文档, 因此不推测正式 URL, 鉴权算法和字段名称.

当前代码中的 `YadeaCloudEvent` 是平台内部临时事件模型, 不是雅迪正式协议.

## 当前数据流

1. `mock` 接口接收定位和车辆状态.
2. Bean Validation 校验请求边界.
3. 合法事件写入 Kafka `vehicle-telemetry`.
4. 消费者幂等写入历史轨迹和最新状态投影.
5. 只有时间更新的事件才覆盖 Redis 最新状态.

数据库先落盘, Redis 后更新. 这样 Kafka 重试或 Redis 短时故障不会造成原始轨迹永久丢失.

## Mock 协议

模拟事件包含:

- 事件编号.
- 车辆编号.
- 设备编号.
- 事件发生时间.
- WGS84 位置.
- 定位精度, 速度, 方向和卫星数.
- 电量和剩余里程.
- 锁状态, 骑行状态和控制器状态.
- 在线状态, 信号强度和故障码.
- 原始扩展字段.

模拟数据中的协议标识固定为 `mock-yadea-cloud-v1`.

当前固定数据包含北京和上海各 100 辆车、共 10,640 条事件. 每辆车的 25 至 60 个定位点均来自高德 v4 骑行路径规划结果, 再按行程时长模拟设备上报. 高德仅用于生成开发样本, 输出 JSON 不保存调用 Key, 正式接入后必须以雅迪设备实际定位为准.

## 正式联调前置资料

需要雅迪提供:

- 测试和生产环境地址.
- `appId`, 密钥和签名规则.
- 时间戳, 随机数和防重放要求.
- IP 白名单和证书要求.
- 推送, 拉取, 重试和确认机制.
- 车辆, 控制器和智能锁的编号关系.
- 定位, 心跳, 电量, 锁状态, 故障和告警字段.
- QPS, 日调用量和消息保留规则.
- 错误码和故障码字典.

## 远程控制

正式协议未确认前不实现真实远程控制.

后续开锁, 关锁, 寻车, 断电和 OTA 等操作必须具备:

- 细粒度权限校验.
- 操作原因和操作审计.
- 指令幂等编号.
- 明确的超时和失败状态.
- 设备执行回执.
- 高风险命令的二次确认.

雅迪正式协议到位后, 优先替换接入边界的鉴权和字段映射, 不改变下游车辆和轨迹模型.
