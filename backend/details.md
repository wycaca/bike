# 后端设计

后端优先支持管理端和运维端. 用户端 App 暂缓, 只保留必要接口边界, 避免前期把复杂度堆到 C 端.

## 技术选型

- 语言: Java 21.
- 框架: Spring Boot 3.
- 数据库: PostgreSQL + PostGIS + TimescaleDB.
- 缓存和状态: Redis.
- 消息队列: Kafka.
- 部署: Docker Compose 起步, 后续迁移到 ECS/SAE/ACK.
- 对象存储: OSS 或同类服务.

选择 Java + Spring 是为了稳定支撑 IoT 上报, 后台管理, 运维任务和后续团队招聘维护. Python 可以支撑 10 万辆, 但需要更强的异步和性能治理经验, 对初创团队不是最低风险路线.

## 服务划分

先做模块化单体, 打包时可以拆成多个无状态进程:

- `admin-api`: 管理端接口, 包含车辆, 城市, 围栏, 订单, 工单, 报表.
- `ops-api`: 运维端接口, 包含工单领取, 换电, 维修, 调度, 扫码核验.
- `iot-ingest`: 车辆上报入口, 接收定位, 电量, 锁状态, 故障, 告警.
- `worker`: 消费 Kafka, 写 Redis 最新状态, 写 TimescaleDB 历史轨迹, 生成告警和工单.

初期也可以只启动一个后端进程. 一旦有真实车辆上报, 优先把 `iot-ingest` 和 `worker` 拆成独立进程, 防止车辆上报影响管理后台.

## 无状态要求

所有后端服务必须无状态:

- 登录态, 验证码, Token 黑名单放 Redis.
- 车辆最新位置, 最新电量, 在线状态, 锁状态放 Redis.
- 分布式锁, 幂等键, 限流计数放 Redis.
- 文件, 图片, 导出报表放对象存储.
- 进程本地内存只允许做短生命周期缓存, 不能作为业务状态来源.

这样后端实例可以随时重启, 扩容, 替换. 高可用通过负载均衡和多实例实现.

## 核心模块

### 权限模块

- 管理员账号.
- 运维员账号.
- 角色和权限.
- 操作审计.

### 城市和区域模块

- 城市管理.
- 运营区.
- 禁骑区.
- 禁停区.
- 停车点.
- 电子围栏.

空间计算使用 PostGIS. 前期只实现多边形和圆形围栏, 不做复杂规则引擎.

### 车辆资产模块

- 车辆档案.
- 二维码绑定.
- 设备编号绑定.
- 车辆状态.
- 电池状态.
- 锁状态.
- 车辆生命周期: 待投放, 运营中, 维修中, 调度中, 报废.

### IoT 上报模块

- 车辆心跳.
- GPS/北斗定位.
- 电量.
- 锁状态.
- 故障码.
- 告警.

写入路径:

1. `iot-ingest` 校验设备签名和消息格式.
2. 写入 Kafka.
3. `worker` 消费消息.
4. 更新 Redis 最新状态.
5. 写入 TimescaleDB 历史轨迹或状态事件.
6. 必要时生成告警或工单.

### 轨迹模块

车辆历史轨迹是核心需求, 使用 TimescaleDB + PostGIS 保存.

轨迹分层:

- 原始轨迹: 保存车辆上报的原始定位点.
- 行程轨迹: 只保存骑行中的轨迹点.
- 简化轨迹: 对行程轨迹做抽稀, 用于客服, 回放, 监管查询.
- 聚合轨迹: 按小时或区域聚合, 用于热力图和报表.

待业务确认:

- 原始轨迹保留多少天.
- 简化轨迹是否永久保存.
- 监管是否要求指定保存年限.

前期先把表结构和归档任务预留出来, 不提前写死保留策略.

### 订单和计费模块

- 扫码开锁.
- 行程开始.
- 行程中状态.
- 还车校验.
- 费用计算.
- 异常订单.
- 退款和补扣.

前期计费规则只支持按城市配置起步价和分钟价. 优惠券, 月卡, 复杂套餐后置.

### 运维工单模块

前期优先实现:

- 低电量换电工单.
- 故障维修工单.
- 乱停调度工单.
- 离线车辆巡检工单.
- 运维员扫码确认.
- 工单处理照片上传.

调度算法先用规则生成, 不做复杂智能调度.

### 报表模块

前期只做管理端需要的核心指标:

- 车辆总数.
- 在线率.
- 可用车辆数.
- 低电量车辆数.
- 今日订单数.
- 今日收入.
- 故障车辆数.
- 工单完成率.
- 区域车辆热力.

报表查询优先读聚合表, 不直接扫描轨迹明细.

## 高可用设计

验证期:

- 单机 Docker Compose, 每日备份数据库.

试运营:

- 2 台后端 ECS.
- API 服务挂负载均衡.
- Redis 使用高可用版或主从.
- RDS 开启自动备份.
- Kafka 使用托管 Serverless 或托管实例.

单城规模:

- `admin-api`, `ops-api`, `iot-ingest`, `worker` 分进程部署.
- API 至少双实例.
- `iot-ingest` 至少双实例.
- `worker` 按 Kafka consumer group 横向扩容.
- 数据库设置慢查询监控和容量告警.

## 成本控制细节

- 后端保持无状态, 避免为了会话粘滞购买复杂负载均衡能力.
- Redis 只保存最新状态和短期状态, 不保存历史轨迹.
- Kafka 只保留 1-3 天原始消息, 不当长期存储.
- TimescaleDB 存核心轨迹, 超期数据归档到 OSS.
- 空闲车辆降低采样频率, 骑行中车辆提高采样频率.
- 报表使用小时级聚合表, 避免频繁扫明细表.
- 前期不做微服务注册中心, 配置中心和服务网格.
- 前期不引入独立 BI 系统, 先用后台页面和 SQL 聚合.
- 前期不做复杂调度算法, 先用规则和人工工单.

## 待确认问题

- 原始轨迹保留多少天.
- 简化轨迹是否永久保存.
- 运营城市是否有监管数据上报接口.
- 支付先接微信, 支付宝, 还是都接.
- 运维端是否必须离线可用.
- 是否需要接入硬件厂商现有协议, 还是自定义设备协议.
